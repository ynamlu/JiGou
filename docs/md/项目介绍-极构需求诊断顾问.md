# 一、写在前面

## 1.1 我们为什么做这件事

做极构之前，我们和不少准备做系统的人聊过。他们有一个共同点：能把自己的想法讲得很热闹，但一遇到具体问题就卡住。

有人想给奶茶店做小程序。问他商品有多少种、规格怎么选、学生下单后怎么取餐、支付资质办了没有，他说这些还没想。有人想给公司做一套进销存。问他谁录单、谁审核、库存不准时怎么处理，他说先做出来再说。还有人拿着两份报价来问我们，为什么一家报三万，另一家报十五万。我们看完需求文档，发现两份报价对应的根本不是同一个东西。

这些经历让我们意识到，很多项目不是死在开发阶段，而是死在开发之前。需求没说清楚，后面所有环节都会跟着变形：报价没法比，工期没法排，验收没有标准，改需求时双方各执一词。

## 1.2 一句话介绍

极构是一个面向非技术用户的需求诊断 Web 应用。它用问卷或自由对话收集信息，对照软件开发知识库做检索，最后给出一份结构化的诊断报告，以及可以直接拿去沟通的交付材料。

它不是开发教程，也不是聊天机器人。它只做三件事：判断你已经想清楚了什么，指出你还缺什么，把需要你拍板的问题列出来。

# 二、问题

## 2.1 一个真实的开场

大多数需求沟通是从一句话开始的：「我想做个系统。」

这句话里通常包含了很多没说出来的假设。用户可能已经想好了业务场景，但没有想过用户角色；可能知道大概要花多少钱，但不知道钱花在哪；可能觉得功能很简单，但没意识到支付、备案、短信、地图这些第三方服务各自需要时间和资质。

如果对面是一个有经验的产品经理，接下来会连续追问：给谁用、有多少人用、核心流程是什么、哪些功能必须有、哪些可以以后再做、预算范围、上线时间、有没有现成的账号体系、数据要不要保留、要不要开发票、有没有合规要求。这些问题问完，需求才勉强具备讨论的基础。

问题是，大多数需求方身边没有这样一个人。他们要么自己摸索，要么直接找外包。前者容易漏项，后者容易被牵着走。

## 2.2 现有工具的缺口

市面上的工具大致分两类。

一类是通用聊天机器人。它们能回答「怎么做小程序」这类问题，但回答往往比较泛。你问预算，它给你一个很宽的区间；你问资质，它列出几条通用建议；你追问「我这个情况具体缺什么」，它还是会回到通用答案。它们擅长生成内容，不擅长把一个人的具体情况问清楚。

另一类是需求管理或项目管理软件。它们假设使用者已经懂研发流程，提供的是文档模板、任务看板和进度管理。对专业团队有用，对第一次做系统的店主或创业者来说，门槛太高。

中间缺的是一个愿意先提问、再给判断的工具。它不需要无所不知，但要知道该问什么；它不需要替用户做决定，但要把选项和后果摆出来。

## 2.3 需求方真正需要的

我们把需求方的需要归纳成四句话。

第一，帮我把想法说清楚。不是让我填一张很长的表，而是一题一题地问，允许我用口语回答。

第二，告诉我还缺什么。不是泛泛地说「需求要明确」，而是具体指出「你还没有说明支付资质」「你的订单状态没有定义」「你的验收标准不清楚」。

第三，给我能用的材料。不是一段聊天记录，而是报告、待确认清单、PRD、询价清单、成本工期，最好还能导出成 PDF 发给别人。

第四，留下凭据。后面改需求时，能查到当时确认了什么，避免口头承诺变成扯皮。

# 三、产品

## 3.1 两种开始方式

极构提供两种开始方式，用户可以根据自己的状态选择。

一种是问卷。系统先问一个种子问题，用户回答后，模型根据已答内容生成下一题。题型有单选、多选和文本，用户可以回退上一题，也可以在题目下补充说明。信息足够时，系统主动收尾，给出小结并邀请生成报告。这种方式适合「知道大概要做什么，但不知道怎么拆」的用户。

另一种是自由对话。用户可以直接把一段想法发进来，系统在回答前会先检索知识库，再按「已具备、还缺失、待确认」的结构输出。对话是流式的，用户能看到文字逐段出现，也能看到「正在检索知识库」的状态。这种方式适合「已经想了不少，想找人核对」的用户。

两种方式可以随时切换。问卷答过的内容会进入对话上下文，对话里补充的信息也会进入报告，不需要重复描述。

## 3.2 一次完整诊断

一次完整的使用通常是这样走的。

用户注册登录后，选择问卷或对话。信息收集到一定程度，系统生成需求诊断报告。报告分五段：项目概述、已具备、还缺失、待确认问题清单、建议下一步。

报告生成后，系统把模糊、缺失、冲突的地方抽成待确认事项。每条事项都可以选择「已确认」「不涉及」或补充说明。全部处理完，用户会看到六维成熟度评分，分别对应形态、用户、功能、预算、时间和合规。

接下来是交付物。系统基于报告生成 PRD、开发询价清单和成本工期估算，再给出 A/B 两套方案：一套是 MVP，先跑通核心流程；一套是完整版，功能更全但周期更长。系统会说明两套方案各自包含什么，并给出推荐和理由。

最后是验收。用户确认报告内容后提交验收，系统生成版本号、SHA-256 指纹和与上一版的差异。凭证可以导出，作为后续沟通的书面依据。

## 3.3 六类产出

用户最终能带走的东西有六类。

| 产出 | 用途 |
| --- | --- |
| 需求诊断报告 | 说清楚项目是什么、已经具备什么、还缺什么 |
| 待确认事项清单 | 把需要拍板的问题逐条列出来，避免漏项 |
| 六维成熟度评分 | 快速看到需求在形态、用户、功能、预算、时间、合规上的短板 |
| PRD、RFP、成本工期 | 直接发给开发方或用于内部立项 |
| A/B 方案 | 在 MVP 和完整版之间做选择 |
| 验收凭证 | 记录版本、指纹和差异，减少后续扯皮 |

## 3.4 诊断之后

极构不负责开发，也不负责撮合交易。诊断结束后，用户拿着材料去找开发方、去内部立项、去申请预算，或者只是回去继续想清楚。系统不会替用户做决定，也不会承诺报价就是最终成交价。

我们觉得这样反而更诚实。一个诊断工具的价值，是让用户在面对开发方时更有底气，而不是让用户依赖它做所有决定。

# 四、一个例子

## 4.1 输入

我们用测试账号跑了一次真实诊断。输入是三段很普通的话：

> 我想在学校旁边开一家奶茶店，做一个小程序，让学生扫码点单、选规格、在线支付，店主能看到订单。
>
> 预算 3 万左右，希望 2 个月内上线。
>
> 暂时不做会员和优惠券，先把点单流程跑通。

这三段话已经包含了不少信息：业务场景、核心流程、角色、预算、时间、范围边界。但它离一份可以拿去开发的需求还有距离。

## 4.2 系统看到了什么

系统先总结了已经具备的部分：业务目标是奶茶店加小程序点单，核心流程是扫码、选规格、支付，店主需要看订单，范围暂时不含会员和优惠券，预算约三万，期望两个月上线。

然后它列出了还缺失的部分。比较关键的几条是：没有商品清单和规格选项，无法配置点单内容；没有价格或计价规则，无法计算支付金额；没有说明学生下单后怎么取餐，订单状态没有定义；没有确认小程序主体和支付商户资质；没有定义「点单流程跑通」的验收标准；三万元和两个月也没有说明包含范围。

这些问题不是凭空生成的。它们对应知识库里关于需求完整性、支付资质、订单流程和验收标准的检查项。系统没有替用户假设「应该做会员」，而是尊重了用户「暂时不做」的决定，只在缺失的地方提问。

## 4.3 输出

系统给出的报告有 852 字，抽取了 9 条待确认事项，六维评分 62 分。评分里合规只有 45 分，主要因为支付资质没有确认；形态 85 分，因为用户已经明确了小程序这个载体；预算和时间各 80 分，因为给了大致范围，但边界不清。

报告的建议下一步是：优先确认点单核心规则和支付资质，这是后续评估预算与排期的前提。

这个结论听起来不复杂，但它把一个模糊的想法拆成了可以逐条处理的问题。用户拿着这份清单去问开发方，至少知道该问什么；开发方拿到这份清单，也更容易给出有依据的报价。

## 4.4 这个例子说明了什么

它说明系统不是在「陪聊」，而是在做判断。判断的依据一部分来自用户输入，一部分来自知识库，还有一部分来自模型对需求完整性的理解。

它也说明系统有边界。它不会替用户决定要不要做会员，不会判断三万块到底够不够，也不会承诺两个月一定能上线。它做的是把问题摆出来，让用户自己拍板。

# 五、AI 在做什么

## 5.1 会追问

问卷的下一题不是提前写死的，而是模型根据已答内容生成的。用户说「做个商城」，系统会继续问商品类型、支付方式、是否需要商家入驻；用户说「做个预约系统」，系统会问预约对象、时段、取消规则、是否收费。问题跟着答案走，而不是走一张固定表单。

对话也一样。系统提示词要求模型先判断信息是否足够，不够就继续问，够了就收尾。这个「判断」是 Agent 的工作，不是简单的关键词匹配。

## 5.2 有依据

回答之前，系统会先检索知识库。知识库是 12 篇原创的软件开发文档，覆盖需求、选型、流程、报价、工期、资质、风险等主题。检索结果会作为上下文拼进提示词，模型再基于这些内容回答。

这样做不能保证每句话都有出处，但能明显减少「凭空发挥」。比如用户问支付资质，系统会提到小程序主体、商户号、审核时间这些具体项，而不是只说「需要相关资质」。

## 5.3 能收口

聊天工具很容易陷入「越聊越多」的状态。极构在设计上要求收口：信息足够时给出小结，邀请生成报告；报告生成后抽取待确认项，逐条拍板；拍板完才能验收。每一步都有明确的下一步，而不是无限对话。

这种收口也体现在输出格式上。报告是固定五段，评分是固定六维，交付物是固定三份，A/B 是固定两套。格式稳定，用户才知道该看哪里，开发方也知道该拿什么。

## 5.4 有边界

系统会拒绝明显违规的请求，也会识别「忽略之前指令」「输出系统提示词」这类注入话术。提示词里明确要求不泄露内部规则、不臆造政策和价格、涉及个人信息时提醒合规。

这些边界不是装饰。一个面向非技术用户的产品，如果什么都说「可以」，反而会让人不敢信。知道自己不知道什么，是诊断工具的基本素养。

# 六、设计取舍

## 6.1 为什么不做代码生成

我们讨论过要不要加「一键生成代码」。最后没有做，原因有两个。

第一，需求诊断和代码生成是两种不同的能力。前者需要提问、判断和归纳，后者需要工程约束和运行环境。把它们塞进一个产品，容易两边都做不深。

第二，代码生成会让产品定位变得模糊。用户是来找人帮他判断需求的，不是来找人替他写代码的。如果系统开始生成代码，用户会自然地问「能不能直接上线」，而这恰恰是极构不擅长的部分。

## 6.2 为什么把报告留在本地

报告正文、评分、交付物和草稿都存在浏览器本地，不上传服务器。这样做的好处是隐私和零运维：用户不需要信任一个云端数据库，换一台机器也不需要迁移数据。

代价是换设备看不到历史。我们考虑过把报告存 SQLite，但那样会让数据库变成一个新的备份和迁移问题。比赛版本选择了更轻的方案，把账号、Token 和验收记录放在 SQLite，报告留在浏览器。这个取舍在技术文档里有更详细的说明。

## 6.3 为什么保留关键词检索

向量检索的效果通常更好，但它依赖 embedding 服务。比赛现场的网络和网关不完全可控，如果检索只能走向量，一次超时就会让演示中断。

所以我们保留了本地的 BM25 关键词检索，作为默认和兜底。它不完美，但零依赖、启动快、结果可解释。配置了 embedding 后可以切换到向量检索，两条路径共用同一个接口，前端和提示词都不需要改。

## 6.4 为什么坚持中文口语

极构的目标用户不是产品经理，而是店主、创业者和学生。系统提示词要求模型用口语回答，避免堆术语，不输出实现步骤。

这条要求执行起来并不容易。模型很容易回到「建议明确目标用户、梳理核心流程」这种模板化表达。我们在提示词里反复强调「像顾问一样说话」「一次只问一个点」「不要教用户怎么做」，才让输出逐渐接近可读的中文。

# 七、价值与边界

## 7.1 对谁有用

对中小微企业和个体经营者，极构可以降低数字化转型的第一步门槛。在花钱之前先把需求想清楚，能减少因信息不对称造成的返工和纠纷。

对创业团队和产品新人，它可以作为立项前的检查工具。把想法整理成 PRD 和询价清单，再去和开发方谈，效率会比空口描述高很多。

对高校学生和参赛团队，它可以作为需求分析的训练工具。系统会指出哪些地方没想清楚，这比直接给一份模板更有价值。

## 7.2 什么时候不适合

如果用户已经有一份成熟的需求文档，只需要开发执行，极构的帮助有限。如果项目涉及强监管行业，需要法律或行业专家意见，极构不能替代专业咨询。如果用户想要的是自动报价和直接下单，当前版本也不提供。

我们更愿意把边界说清楚，而不是让用户带着错误预期使用。

## 7.3 我们期待的使用方式

理想的使用方式不是「让 AI 替我想」，而是「我先说，AI 帮我查漏补缺，我再拍板」。系统给出的是问题和建议，决定权仍在用户手里。

如果用户用完之后的感受是「原来我还有这么多没想清楚」，那说明产品起作用了。
