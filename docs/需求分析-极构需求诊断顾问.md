# 一、文档目的与范围

## 1.1 为什么单独写需求分析

技术文档回答的是「系统怎么实现」，项目介绍回答的是「产品是什么」。这两份文档都默认需求已经清楚，但实际情况不是这样。极构本身就是一个帮别人梳理需求的工具，如果自己的需求分析说不清楚，后面的设计和测试就没有依据。

这份文档补的就是这一段：我们观察到了什么问题，判断哪些人需要它，哪些功能必须有、哪些可以以后再做，以及做到什么程度算完成。

## 1.2 本文回答什么

全文围绕四个问题展开。

第一，需求方到底卡在哪里。笼统地说「不会写需求」没有意义，真正的问题是不知道该问什么、判断不了报价、漏掉资质、验收没有标准。

第二，极构为谁做。目标用户不只是「中小企业」，还包括创业团队、产品新人和高校学生。不同人群的使用动机不一样，功能优先级也不一样。

第三，第一期做什么。比赛周期有限，我们把功能分成 P0、P1、P2 三档，先保证一次完整诊断能走通，再补交付物和体验。

第四，怎么判断做完了。每条关键需求都对应可验证的验收条件，测试文档里的用例就是按这些条件写的。

## 1.3 与其它文档的关系

| 文档 | 关注点 |
| --- | --- |
| 本文 | 问题、用户、功能边界、优先级、验收条件 |
| 项目介绍 | 面向非技术读者的产品说明与使用案例 |
| 技术文档 | 系统结构、AI 方案、关键实现与工程取舍 |
| 测试文档 | 测试环境、用例、实测结果与缺陷记录 |

# 二、问题定义

## 2.1 需求方处在什么位置

准备做系统的人，通常不是完全没有想法。他们能说出业务场景，甚至能画出大概的流程，但很难把想法整理成开发方可以直接使用的材料。

这和「不懂技术」不是一回事。很多需求方能讲清楚自己要什么，只是不知道哪些信息是开发必需的。比如他知道要做一个点单小程序，但不知道商品规格、取餐方式、支付资质、订单状态这些内容需要在开发前定下来。等到开发方问起，才发现自己还没想。

## 2.2 四类典型困难

我们把常见的困难归成四类，后面的功能设计基本都对应这四类。

第一类是表达困难。用户知道「想做个系统」，但说不清角色、流程、边界和优先级。问得细一点，回答就开始重复；问得专业一点，又听不懂。

第二类是判断困难。两份报价差了好几倍，用户不知道差异在哪里，也不知道哪些钱是必须花的。没有需求清单，报价就没有可比性。

第三类是完整性困难。支付资质、备案、短信、地图、发票、数据保留，这些事项在业务描述里往往不会出现，但会直接影响工期和成本。

第四类是验收困难。口头确认多、书面记录少，改需求时容易扯皮。用户说不清「做到什么程度算完成」，开发方也不敢把话说死。

## 2.3 现有方案为什么不够

通用聊天机器人能回答「怎么做一个系统」，但回答偏通用。用户问「我这个情况还缺什么」，它还是会回到目标用户、核心流程这类模板。它擅长生成内容，不擅长把一个人的具体情况问出来。

需求管理软件和文档模板更专业，但默认使用者懂研发流程。让一个准备开奶茶店的人直接填 PRD 模板，填不了几行就会放弃。

外包公司会问，但提问有成本，而且双方立场不同。需求方希望少花钱，开发方希望范围清楚，提问的过程本身就可能变成博弈。

这中间缺的是一个站在需求方一侧、愿意先提问、再给判断的工具。它不需要无所不知，但要知道该问什么；不需要替用户做决定，但要把选项和后果摆出来。

## 2.4 机会点

机会不在于再做一个聊天机器人，而在于把「需求诊断」拆成可执行的动作：提问、对照检查项、生成报告、逐条确认、形成验收凭证。

模型的能力适合做前三步，尤其是把口语化的描述归纳成结构化的已具备、还缺失和待确认。后两步更多是产品设计：用什么方式让用户逐条拍板，怎么把确认结果固定下来，怎么在改需求时看出差异。

# 三、用户与场景

## 3.1 用户分类

| 用户类型 | 典型情况 | 最在意什么 | 使用动机 |
| --- | --- | --- | --- |
| 个体经营者与小微企业主 | 想点单、预约、会员、进销存等业务系统，没有技术团队 | 预算、工期、能不能落地 | 找开发前先把需求想清楚，避免被报价牵着走 |
| 创业团队与产品新人 | 有想法，需要立项、融资或对外询价 | 需求是否完整、能不能写成材料 | 把想法整理成 PRD 和询价清单 |
| 高校学生与参赛团队 | 做课程项目、竞赛作品或创业计划 | 结构规范、上手快 | 快速梳理需求，形成可提交的文档 |

这三类人的共同点是缺少需求分析经验，不同点是容忍度。个体经营者对时间和费用更敏感，创业团队更在意材料的完整度，学生更在意上手成本。功能优先级要同时照顾这三种情况。

## 3.2 三个典型画像

第一个画像是学校旁边的奶茶店店主。他想做扫码点单，预算三万，希望两个月上线。他能说清商品大概有哪些，但没想过规格、加料、取餐叫号、支付资质和退款流程。他不需要一份很长的 PRD，只需要知道现在缺什么、先补哪几项。

第二个画像是准备立项的创业团队负责人。他有一份商业计划，需要把产品需求整理成可以给开发方看的东西。他关心的是功能边界、优先级和成本区间，也希望材料看起来专业，能在内部评审或融资沟通中使用。

第三个画像是参加比赛的学生团队。他们有明确的功能设想，但需求文档通常写得比较散。他们需要一套结构，把功能、角色、流程和非功能要求补齐，也需要在答辩时解释清楚为什么这样设计。

## 3.3 关键使用场景

| 场景 | 用户目标 | 系统动作 | 可能的打断 |
| --- | --- | --- | --- |
| 只有一个模糊想法 | 先看看自己要做什么 | 用问卷逐题追问 | 用户答不下去，需要示例或跳过 |
| 已经写了一些内容 | 找人核对有没有漏项 | 自由对话加知识库检索 | 回答太长，用户抓不住重点 |
| 拿到报告后 | 把没想清楚的事定下来 | 抽取待确认事项，逐条拍板 | 用户不确定，需要「暂不涉及」 |
| 准备找开发方 | 拿到能询价的材料 | 生成 PRD、RFP、成本工期 | 模型生成失败，需要空状态提示 |
| 改完需求 | 留下书面凭据 | 重新验收，生成版本和 diff | 用户忘记上一版确认了什么 |

## 3.4 用户旅程

一次完整使用从登录开始，经过诊断、报告、确认、评估、交付和验收。每一步都允许回退：问卷可以回上一题，对话可以停止，报告可以修订后重新验收。

旅程中有两个容易流失的点。一是第一次提问之后，如果问题太专业或太长，用户可能直接退出；二是报告生成需要时间，如果没有状态反馈，用户会以为页面卡住。产品设计在这两处做了针对性处理：问题尽量口语化、一次只问一个点；报告生成显示加载状态，对话逐字输出。

# 四、需求获取

## 4.1 需求来源

这份需求分析没有做大规模问卷，也没有严格的用户访谈样本。主要来源有四类。

一是身边案例。我们和准备做系统的店主、同学、创业团队聊过，听他们描述想做什么、卡在哪里、被开发方问过什么问题。这些交流不是正式访谈，但提供了很多具体说法。

二是公开资料。包括常见的企业信息化项目流程、外包报价构成、小程序和支付资质要求、软件项目验收习惯。这些内容帮助我们判断哪些问题是普遍存在的，而不是个别情况。

三是知识库整理。我们把需求文档、技术选型、开发流程、报价、工期、资质、风险等主题写成 12 篇文档，写的过程本身也是一次需求梳理：哪些检查项应该出现在诊断里，哪些只是背景知识。

四是试用反馈。系统做出主流程后，我们请同学试用，观察他们在哪一步停顿、哪些提示看不懂、哪些按钮找不到。测试文档里的浏览器检查和缺陷记录，有一部分就来自这些反馈。

## 4.2 从案例到检查项

需求不是直接从「用户说想要什么」变成功能列表的。中间有一个转换过程：先把案例拆成问题，再把问题归成检查项，最后决定哪些检查项由系统自动完成。

以奶茶店小程序为例。用户说「扫码点单、选规格、在线支付，店主看订单」，这句话可以拆成商品、规格、价格、下单、支付、取餐、订单状态、退款、店主通知等检查项。系统不需要替用户回答这些，但要在诊断中把它们问出来。

再以「预算三万、两个月上线」为例。这句话是约束，不是需求。系统需要继续问：三万包含设计、开发、服务器、认证和支付手续费吗？两个月是从签约算还是从上线算？这些边界不清楚，后面一定会有争议。

## 4.3 知识库怎么形成

知识库的 12 篇文档按「需求方最常问什么」分主题，没有写成百科。每篇有一个明确主题，标题就是检索时的主题标签，正文用短段落和清单写成，方便切片和引用。

选择这个规模，是因为再大的知识库会带来两个问题：切片质量难控制，检索结果容易泛；维护成本高，比赛周期内无法保证内容准确。12 篇文档覆盖不了所有行业，但能覆盖大部分中小型项目的第一轮判断。

## 4.4 需求取舍过程

需求讨论中最常见的分歧是「要不要做得更多」。有人希望加代码生成，有人希望加项目管理，有人希望直接对接外包报价。我们最后没有加。技术不是主要障碍，真正的顾虑是这些功能会破坏产品定位。

极构的核心价值是判断需求，不是执行开发。如果加入代码生成，用户会自然地问能不能直接上线；如果加入项目管理，产品会变成另一个协作工具；如果直接报价，系统就要为价格准确性负责。这些都不在当前能力和周期内。

取舍的标准有三条：是否直接服务于「把需求说清楚」；是否能在本地单机环境稳定运行；是否有明确的验收方式。三条都满足的进 P0 或 P1，只满足一部分的放 P2，不满足的暂时不做。

## 4.5 需求获取的局限

必须承认，这份需求分析的样本有限。我们没有做统计意义上的用户调研，也没有覆盖多个行业和地区。很多判断来自身边案例和公开资料，可能存在偏差。

第二个局限是用户说出来的需求和真实需求不一定一致。用户说自己要「一个简单的系统」，实际使用中可能对性能、权限、数据保留有更高要求。系统通过追问和知识库检查项来弥补，但不能完全替代深入访谈。

第三个局限是比赛周期。需求分析、设计、开发、测试和文档是并行推进的，很多结论是在实现过程中修正的，不是一次性推导出来的。本文记录的是当前版本的判断，后续如果继续迭代，需要重新审视。

# 五、功能需求

## 5.1 需求编号与优先级

功能需求用 FR 编号，非功能需求用 NFR 编号。优先级定义如下。

| 优先级 | 含义 | 判断标准 |
| --- | --- | --- |
| P0 | 必须完成 | 缺了它，一次完整诊断走不通 |
| P1 | 应该完成 | 影响交付质量或用户信任，但不阻断主流程 |
| P2 | 可以延后 | 体验补充，不影响核心价值 |

## 5.2 账号与数据

账号体系是 P0。原因很实际：报告、验收记录和草稿需要按人隔离，没有账号就无法证明数据属于谁。注册使用手机号，密码要求至少 8 位并包含三类字符；登录后签发 Token，接口用 Bearer Token 鉴权。

数据隔离也是 P0。报告正文存在浏览器本地，按账号加键名；验收记录存在 SQLite，按账号和项目标识查询。切换账号后看不到对方的数据，注销账号时级联删除该账号的 Token 和验收记录。

## 5.3 诊断入口

诊断提供问卷和自由对话两种入口，都是 P0。

问卷适合不知道从哪说起的人。系统先问一个种子问题，之后根据已答内容生成下一题，支持单选、多选、文本和补充说明。用户可以回上一题，也可以在信息足够时主动结束。

自由对话适合已经有一些想法的人。用户直接描述项目，系统先检索知识库，再按「已具备、还缺失、待确认」输出。对话是流式的，可以停止生成，已经输出的内容保留。

两种入口共享同一份问卷上下文。用户在问卷里答过的内容，切换到对话时不会重复问；对话里补充的信息，也会进入报告生成。

## 5.4 报告与确认

报告生成是 P0。报告固定五段：项目概述、已具备、还缺失、待确认问题清单、建议下一步。固定结构能降低阅读成本，让用户知道该看哪里。

待确认事项抽取是 P0。报告里的模糊、缺失、冲突项要单独拎出来，逐条让用户选择「已确认」「不涉及」或补充说明。全部处理完才能提交验收，避免漏项。

这一步的产品价值最高，也最容易做虚。如果只是把报告里的句子再列一遍，用户没有获得感；必须做到每条都能指向一个具体决策，比如「支付资质是否具备」「取餐流程怎么走」「验收标准是什么」。

## 5.5 评估与交付

六维评分是 P1。形态、用户、功能、预算、时间、合规六个维度各 0 到 100 分，附最多 5 条风险提示。评分的作用是让用户快速看到短板，不需要把它当成考试。分数低的地方，通常就是待确认事项集中的地方。

交付物是 P1。一次生成 PRD、RFP 和成本工期估算。PRD 面向开发和设计，RFP 面向询价，成本工期面向决策。A/B 方案也是 P1，给出 MVP 与完整版的对比、适用阶段和推荐理由。

这些内容依赖模型生成，失败时返回空结构，前端展示空状态。宁可让用户看到「暂未生成」，也不要用一段看起来像真的假数据糊弄。

## 5.6 验收与导出

验收是 P1，但对「留下凭据」这个用户目标来说是关键。每次验收计算报告正文和决策项的 SHA-256 指纹，按账号和项目标识递增版本号，并与上一版做行级 diff。凭证可以导出 Markdown。

导出包括 Markdown、PDF 和长截图，都是 P2。Markdown 适合继续编辑，PDF 适合直接发送，长截图适合发到聊天窗口。导出不是诊断的核心，但决定了结果能不能进入真实沟通。

## 5.7 内容与辅助

模板库和案例库是 P2。内置 6 套行业模板和 2 个案例成品，支持搜索、预览、导出和「以此开始诊断」。它的作用是降低第一次使用的门槛，不是替代诊断。

我的图纸是 P1。按账号归档报告，支持按标题或日期搜索、删除二次确认，并用徽章标出草稿、已验收、评分和交付物状态。没有这个页面，用户做完一次诊断就找不到结果。

## 5.8 功能需求清单

| 编号 | 需求 | 优先级 | 验收条件 |
| --- | --- | --- | --- |
| FR-01 | 手机号注册 | P0 | 非法手机号 400，弱密码 400，重复注册 409，正常注册 200 |
| FR-02 | 登录与 Token 鉴权 | P0 | 正确登录返回 Token，无 Token 或伪造 Token 访问受保护接口返回 401 |

| FR-05 | 自由对话 | P0 | 流式返回，显示检索状态，可停止生成，保留已输出内容 |
| FR-06 | 生成诊断报告 | P0 | 输出五段结构，内容只引用用户提供的信息 |
| FR-07 | 抽取待确认事项 | P0 | 每条包含标题、说明和类型，支持逐条决策 |

# 六、非功能需求

## 6.1 性能与等待

本地应用的性能压力主要不在网络，而在模型生成。问卷出题实测约 10.6 秒，报告生成约 58.8 秒。这个时间无法完全消除，产品能做的是把等待变得可理解：对话逐字输出，报告按钮显示加载状态，生成过程允许停止。

首屏要求是本地打开后很快可交互。前端构建成单文件，路由按页懒加载，未配置 Key 时也不初始化 Agent 和向量库，避免启动时做无关工作。

## 6.2 可用性与降级

外部依赖只有模型网关和可选的向量服务。模型不可用时，页面仍要能打开，AI 接口给出明确提示；向量服务不可用时，检索自动回落到本地 BM25。这条降级路径是硬要求，不是可选项。

比赛现场的网络不可控。如果演示到一半因为一个外部服务超时而中断，功能做得再多也没有意义。所以系统在启动、检索、生成三个环节都做了失败处理。

## 6.3 安全与隐私

密码不能明文存储，接口必须鉴权，Key 不能进入仓库。输入侧拦截明显的危险请求和提示词注入，输出侧对异常信息做密钥脱敏。

隐私方面，报告正文、评分、交付物和草稿只存在浏览器本地；账号、Token 和验收记录存在本地 SQLite；不依赖第三方云数据库。模型推理会把必要上下文发给网关，这一点在界面上有说明。

## 6.4 兼容与可维护

界面以中文为主，桌面和手机浏览器都能使用。320px 宽度下不能出现横向滚动，表格和卡片改为单列。启动脚本兼容 Windows、macOS 和 Linux，Windows 下处理 `npm.cmd`、`taskkill` 和 UTF-8 输出。

可维护性方面，环境变量集中管理，依赖版本固定，启动一条命令完成。代码风格使用 Ruff，Python 行宽 110。后端有 12 个 unittest 接口用例，前端仍以人工检查为主。

## 6.5 非功能需求清单

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| NFR-01 | 首屏可交互 | 本地打开登录页无明显白屏，静态资源由 FastAPI 托管 |
| NFR-02 | 流式输出 | 对话逐字返回，事件类型可被前端解析 |
| NFR-03 | 检索降级 | 未配置向量库时 `/api/health` 显示 keyword，检索仍可用 |
| NFR-04 | 无 Key 可用 | 页面正常打开，AI 接口返回 503 或流式错误提示 |
| NFR-05 | 输入限制 | 单条输入超过 2000 字时提示精简 |
| NFR-06 | 安全存储 | 密码使用 PBKDF2-SHA256 加盐哈希，数据库无明文 |
| NFR-07 | 输出脱敏 | 异常信息中的 Key 和 Token 被替换为 `***` |
| NFR-08 | 响应式 | 320 / 390 / 834 / 1440 宽度无横向滚动 |
| NFR-09 | 可维护 | `python run.py` 可完成依赖、构建、启动 |
| NFR-10 | 可测试 | 后端接口用例可通过 unittest 运行，且不污染运行数据库 |

# 七、数据需求

## 7.1 数据分类

| 数据 | 内容 | 存放位置 | 保留周期 |
| --- | --- | --- | --- |
| 账号 | 手机号、密码哈希、盐、注册时间 | SQLite users 表 | 直到用户注销 |
| 登录凭证 | Token、账号、签发时间 | SQLite tokens 表 | 直到登出或重新登录 |
| 验收记录 | 报告正文、决策项、指纹、版本、diff | SQLite acceptances 表 | 直到用户注销 |
| 报告与草稿 | 报告、评分、交付物、分析草稿 | 浏览器 localStorage | 直到用户删除或清理浏览器 |
| 知识库 | 12 篇 Markdown 文档 | `backend/kb` | 随代码版本保留 |

## 7.2 数据生命周期

注册时创建账号和密码哈希；登录时删除该账号的旧 Token，写入新 Token；验收时写入一条记录并递增版本；注销时删除该账号的 Token、验收记录和账号本身。

报告正文不写入 SQLite，这是有意的。报告体积较大，且属于用户隐私；放在浏览器本地可以减少服务端存储和备份压力。代价是换设备看不到历史，这一点在项目介绍和技术文档里都写明了。

## 7.3 数据隔离

浏览器存储的键名包含账号：`jg_session` 保存当前会话，`jg_archive:<手机号>` 保存报告归档，`jg_analysis_draft:<账号>` 保存草稿。SQLite 查询按 username 过滤，验收版本按 username 和 project_key 计算。

隔离的验收条件是：两个账号对同一个 project_key 分别验收，各自从 v1 开始；注销一个账号后，另一个账号的数据仍然存在。测试文档里有对应用例。

# 八、约束与假设

## 8.1 运行约束

系统运行在本地电脑上，需要 Python 3.11 以上和 Node.js 20.19 以上。生产模式由 FastAPI 托管前端构建产物，只需要一个进程，不依赖 Docker、Nginx 或云数据库。

这个约束来自比赛场景：评审老师不应该为了运行一个作品去装一堆服务。代价是系统不适合多实例并发，SQLite 和浏览器本地存储都假设单机单用户。

## 8.2 模型约束

模型通过 OpenAI 兼容网关调用，需要有效的 API Key。默认型号是 `deepseek-v4.1-flash-1017`，温度设为 0，结构化输出尽量稳定。网关的超时、限流和返回格式变化都不完全可控，系统必须做异常处理。

模型输出存在波动。同一组输入，报告长度、评分和待确认项数量都可能变化。需求上不承诺「每次生成完全一致」，只承诺结构稳定、失败有提示、结果可修改。

## 8.3 业务假设

我们假设用户愿意花十到二十分钟完成一次诊断，并且能提供基本的项目信息。如果用户只想在一分钟内拿到报价，极构不适合。

我们假设用户会把报告用于真实沟通，而不是只当作聊天记录。因此报告的结构、措辞和导出能力都比「聊得热闹」更重要。

我们还假设用户对隐私敏感，不希望把项目细节上传到一个陌生的云端数据库。这是报告放在浏览器本地的原因之一。

# 九、范围与优先级

## 9.1 MVP

MVP 的目标是让一次诊断从开始走到验收。范围包括账号、问卷、自由对话、报告、待确认事项、六维评分、验收版本和基础导出。

这些功能缺一不可。没有账号，数据无法隔离；没有问卷或对话，信息收集不完整；没有报告，用户拿不走结论；没有待确认事项，报告只是一段文字；没有验收，改需求时没有凭据。

## 9.2 第二版

第二版补交付物、A/B 方案、报告修订、模板库和我的图纸。它们不阻断主流程，但明显提升可用性。尤其是交付物和 A/B 方案，直接决定用户能不能拿结果去询价或立项。

模板库和我的图纸属于体验层。模板降低第一次使用的门槛，我的图纸让用户找得到历史结果。它们放在 P1 或 P2，是因为没有它们也能完成一次诊断。

## 9.3 暂不纳入

本期不做代码生成、项目管理、团队协作、云端同步、语音和图片输入、自动报价下单。原因在 4.4 节已经说明：这些功能会改变产品定位，或者超出当前周期和能力。

## 9.4 版本取舍理由

取舍的标准很朴素：哪个功能更接近用户问题，就先做哪个。用户最痛的是说不清需求和验收没凭据，所以这两块优先；报价和交付物重要，但可以基于报告生成，放在第二版；模板和导出是加分项，放在最后。

# 十、验收标准

## 10.1 主流程验收

主流程的验收条件是：注册登录后，能用问卷或对话完成信息收集，生成五段式报告，抽取待确认事项并逐条决策，得到六维评分，提交验收并拿到版本号和指纹，最后能导出 PDF 或 Markdown。

这条路径必须一次走通，中间不能要求用户理解技术概念，也不能出现未处理的异常。

## 10.2 关键需求验收

| 需求 | 验收方式 | 对应测试 |
| --- | --- | --- |
| FR-01 注册 | 非法手机号、弱密码、重复注册分别返回 400、400、409 | TC-03 至 TC-05 |
| FR-02 登录鉴权 | 正确登录 200，错误密码 401，无 Token 401 | TC-06 至 TC-09 |
| FR-04 问卷 | 提交已答内容后返回下一题，字段完整 | 真实模型链路 |
| FR-06 报告 | 输出五段结构，内容不超出用户输入 | 真实模型链路 |
| FR-07 待确认 | 返回数组，字段包含标题、说明、类型 | 真实模型链路 |
| FR-12 验收版本 | 首次 v1，再次 v2，diff 含差异行 | TC-15 至 TC-17 |
| FR-13 PDF 导出 | 返回 `%PDF`，空内容 400 | TC-18、TC-19 |
| FR-16 路由守卫 | 清空会话后访问受保护页面跳登录 | 浏览器检查 |
| FR-17 数据隔离 | 两个账号同项目各自 v1 | TC-17 |
| NFR-04 无 Key | 对话返回 error 事件，报告接口 503 | TC-20、TC-21 |

## 10.3 不通过的情况

出现以下任一情况，视为验收不通过：主流程中断且没有可读提示；账号之间能看到对方数据；未配置 Key 时页面无法打开；导出的 PDF 打不开；验收版本号不递增或 diff 缺失；移动端出现横向滚动。

这些条件和测试文档里的用例对应，不靠主观判断。

# 十一、需求变更与风险

## 11.1 变更记录方式

需求变更不靠口头同步。每次报告修订都会生成新版本和 diff，验收记录里保留指纹和决策项。文档层面的变更记录在版本号和提交历史里，重大调整会同步到技术文档和测试文档。

新增需求必须先说明用户问题、优先级和验收条件，再决定是否进入当前版本。只是「看起来应该有一个」的功能，不进入 P0。

## 11.2 主要风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 模型输出波动 | 报告长度、评分、待确认项数量不稳定 | 固定结构、温度 0、解析容错、允许修订 |
| 报告生成慢 | 用户等待接近一分钟 | 加载状态、流式对话、允许停止 |
| BM25 召回有限 | 冷门行业回答偏泛 | 知识库扩展、可配置向量检索 |
| 本地存储不跨设备 | 换电脑看不到历史 | 明确说明，后续迁移 SQLite 或导出导入 |
| 需求范围膨胀 | 主流程做不完 | P0/P1/P2 分级，变更需说明验收条件 |
| Key 泄露 | 安全和费用风险 | 环境变量、忽略文件、输出脱敏 |

## 11.3 应对原则

风险应对遵循两个原则：能降级的不阻断，能说明的不隐瞒。

模型和向量服务异常时，系统降级到可用状态；数据不跨设备、检索有局限这类产品边界，直接在文档和界面上说明，不让用户带着错误预期使用。

# 十二、结论

极构的需求并不复杂，难的是克制。用户需要的是一个能提问、能判断、能留下材料的工具，不是一个什么都能做的平台。我们把功能收在诊断、报告、确认、验收这条线上，把代码生成、项目管理、自动报价这些诱惑挡在外面。

这份需求分析的可信度受样本限制，很多判断来自身边案例和公开资料。它足以支撑当前版本的设计和测试，但如果要走向真实产品，还需要更系统的用户研究、更多的行业样本和更长的观察周期。

至少现在，每条 P0 需求都有明确的用户问题和验收条件，每个关键功能都能在测试文档里找到对应记录。这是我们认为当前阶段应该做到的程度。
